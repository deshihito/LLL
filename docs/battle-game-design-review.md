# バトルシステム改善提案

## 結論

現状の課題は、UIの情報量だけではありません。**試合ルールの正本が複数あり、実装・試し切り・対人バトルで挙動が一致していない**ことが最大の問題です。

先に動的CSSや演出を増やすと、プレイヤーは「何が起きたのか分からない状態が、派手に動くだけ」になります。実装順は次の通りに固定すべきです。

1. **ルールを一つの仕様書・一つの実行系に統合する**
2. **バトルの状態遷移を明示的なフェーズとして定義する**
3. **プレイヤーの意思決定に必要な情報だけを常時表示する**
4. **詳細情報はカード展開・長押し・モーダル・リプレイで段階表示する**
5. **最後に動的CSS・演出・インタラクションを加える**

---

## 1. 現状の重大な仕様不一致

### 1.1 TypeScriptエンジンと本番SQLが別ゲームになっている

現在、試し切りは `apps/web/src/lib/battle/engine.ts`、対人バトルはSupabaseのSQL関数が実行系です。両者で以下が分かれています。

| 項目 | 試し切り / TypeScript | 対人 / SQL | 問題 |
|---|---|---|---|
| 行動種別 | `use_skill` / `use_support` / `end_turn` | SQL側で別途実装 | 試し切りで成功した操作が対人で失敗し得る |
| アクションカード | 初期配置外は手札に入る | マッチング時に一部が `deck` へ入る | UIに表示されず、出す対象が存在しない |
| パーツ | 型にはあるが、エンジンの正式な配置処理がない | 追加migrationで装着処理を追加中 | 既存バトルとの互換性が不明 |
| スキル条件 | スキルの `conditions` を実行時に評価していない | SQL側も技ごとの条件評価が不十分 | 条件付きカードの説明と挙動が一致しない |
| 効果 | 未対応効果が `effect_skipped` になる | SQL側の対応範囲も別 | カード生成時に合法でも実戦で無効になる |
| 状態異常 | statusを保持するだけのものがある | SQL側も効果ごとに処理が異なる | stun / burn / guard_break等の意味が不明確 |
| ターン終了 | 技の `turn_behavior` で自動終了 | SQL側の分岐実装 | 「続けて行動できる条件」がプレイヤーに見えない |
| コスト | activeは100へ正規化 | SQLも概ね100 | 旧カード・旧テスト・表示文言に50等の残骸がある |

### 1.2 アクションカードのライフサイクルが未定義

最低限、次を仕様として決める必要があります。

- デッキに入るカードの種類
- 初期場に出る枚数
- 手札に来る枚数とタイミング
- 場に出すコスト
- 場の最大枚数
- 場から破壊された後に補充するか
- パーツは手札に来るのか、親アクションに自動付属するのか
- 付属パーツはカード枠を消費するのか
- アクションを出す操作がターンを消費するのか

現状は「デッキではアクションとパーツが存在する」「バトルではアクションは場に出る」「UIでは手札からフリックできる」が混在しています。これではゲームプレイの戦略が成立しません。

### 1.3 勝利条件と場の上限が噛み合っていない

現在は「3枚破壊」が勝利条件ですが、初期の場は最大2枚です。追加カードの投入・補充ルールが明確でない場合、3枚破壊へ到達する方法が不透明です。

推奨する選択肢は以下のどちらかです。

- **案A: 2枚場 + 3枚撃破**
  - 破壊されたカードの代わりに、手札から1枚を補充
  - 破壊されたカードは撃破数に加算
  - 3枚目を倒した時点で勝利
- **案B: 3枚場 + 3枚撃破**
  - 初期から3枚を場に置く
  - UIとカード情報量が増えるため、スマホでは案Aを推奨

### 1.4 技効果の対象と条件が危険

実装上、クライアントから送られた対象を技効果に渡し、効果ごとの `target` を完全には強制していません。これにより、カード定義が `self` でも敵を対象にできる余地があります。

また、次の効果は別々に仕様化すべきです。

- `damage`: ダメージ計算
- `heal`: 回復量
- `stat_modifier`: 基礎値への一時補正
- `status_apply`: 状態異常
- `counter`: 被弾時の一度だけの反撃
- `follow_up`: 命中時の追撃
- `equip_part`: パーツ装着

現在は未対応効果を `effect_skipped` として処理するため、生成カードが見た目上は完成していても、ゲーム内では何もしない可能性があります。**未対応効果を保存可能にしない**ことが必要です。

## 2. まず確定すべきバトルルール

### 2.1 推奨する最小ルール

最初の正式版は、以下に限定します。

- 1対1
- 自分の場は最大2アクション
- 初期場は1アクション
- 手札からアクションを1枚ずつ補充
- パーツは親アクションに最大2枚まで装着
- サポートは手札から即時使用
- アクティブ技は100 AP
- パッシブ技はAP 0、条件成立時のみ自動発動
- 1ターン中のアクティブ技は最大2回
- 技が `end` の場合は行動後にターン終了
- 技が `continue` の場合は同じカードで追加行動可能。ただし最大2回
- 場のカードが破壊されたら、次の自分のターン開始時に手札から補充
- 3枚撃破で勝利
- 勝敗決定後は入力を全て無効化

このルールなら、場の視認性を保ちながら「カードを出す」「パーツを付ける」「技を選ぶ」「サポートを切る」という4種類の判断が成立します。

### 2.2 状態機械

バトルを次の状態として扱います。

```text
LOBBY
  ↓ マッチング成立
OPENING
  ↓ 初期配置確認
PLAYER_TURN
  ├─ PLAY_ACTION
  ├─ EQUIP_PART
  ├─ USE_SUPPORT
  ├─ USE_SKILL
  ├─ RESOLVE_EFFECTS
  ├─ REPLACE_DEFEATED
  └─ END_TURN
       ↓
OPPONENT_TURN
  ↓
RESULT
```

各状態で許可される操作をAPIでも制限します。UIだけでボタンを隠すのでは不十分です。

### 2.3 ルールの正本

`engine.ts`を唯一のルール定義にし、以下のどちらかへ統一します。

- SQLを実行系として残すなら、TypeScriptはSQLと完全一致するテスト用ミラーにする
- TypeScriptを正本にするなら、SQL関数は同じ仕様のトランザクション実装として書き直す

推奨は、**ルール計算を純粋なTypeScript関数に集約し、サーバー側は同じ入力・出力契約で永続化する構成**です。少なくとも、同じシナリオをTypeScriptとSQLの両方で実行して結果を比較する契約テストを追加してください。

## 3. 情報設計: 常時表示を減らす

### 3.1 常時表示するもの

バトル画面に残すのは、次の5ブロックだけで十分です。

1. **ターン・手番**
2. **敵の場**
3. **中央の解決エリア**
4. **自分の場**
5. **手札**

ポイントは「現在のAP合計」ではなく、**現在選択中カードのAP**を主表示にすることです。AP合計はカードごとの支払い能力を表さないため、合計値だけでは意思決定に使いにくいです。

### 3.2 詳細は段階表示にする

| 操作 | 表示する情報 |
|---|---|
| タップ | カード選択、短いハイライト |
| 長押し | カード詳細、技説明、効果範囲 |
| 場カードを上スワイプ | 技・状態・パーツの詳細シート |
| 手札カードを中央へフリック | 解決プレビュー |
| 解決プレビューを再タップ | 実行確定 |
| ダメージ数字をタップ | 計算内訳 |
| ターン表示をタップ | 直近ターンの履歴 |
| 結果画面を上スワイプ | リプレイ・勝因・敗因 |

これにより、通常時は文字量を減らしつつ、必要な時だけ情報量を増やせます。

### 3.3 画面遷移を増やす際の注意

ページを頻繁に切り替えるのではなく、**同じバトル画面の上に一時的なレイヤーを出す**べきです。

- カード詳細シート
- 効果対象選択レイヤー
- 解決プレビュー
- ダメージ計算レイヤー
- バトル結果レイヤー

バトル中に別ページへ移動すると、盤面・手番・手札の文脈が切れます。情報量を減らす目的なら、ページ遷移よりも「モーダル」「ボトムシート」「カードの展開」を優先します。

## 4. フリック操作のゲームデザイン

### 4.1 フリックは操作ではなく意思決定にする

ただドラッグできるだけでは、ゲーム性になりません。カード種類ごとに行き先と意味を固定します。

| カード | 入力 | 意味 |
|---|---|---|
| アクション | 中央へフリック | 場に配置 |
| パーツ | 対応するアクションへフリック | 装着 |
| サポート | 中央へフリック | 使用 |
| 場のカード | 上へフリック | 技選択シートを開く |
| 場のカード | 横へスワイプ | 対象を切り替える |

### 4.2 誤操作防止

フリックだけで即時確定すると、スマホでは誤操作が多くなります。推奨は次の二段階です。

1. フリック中にカードを中央へ吸着
2. 解決エリアに「効果・対象・コスト」を短時間表示
3. 指を離した時に確定
4. 取り消しはカードを手札へ戻すスワイプ

ただし、サポートのように結果が明確な操作は即時確定してもよいです。カードごとに確認の重さを変えます。

### 4.3 動的CSSの使いどころ

動的CSSは装飾ではなく、状態伝達に使用します。

- 自分のターン: 盤面外周を青く脈動
- 相手のターン: 手札と操作対象を暗くして入力不可を示す
- AP不足: 技カードを赤くするのではなく、コスト部分だけを低彩度化
- 正しい装着先: パーツと親カードの間に吸着ラインを表示
- 対象外カード: 透明度を下げる、位置は変えない
- 有効なターゲット: 輪郭を太くし、対象範囲を短い光の線で示す
- ダメージ: 数字を出すだけでなく、HPバーの減少と被弾方向を同期
- 状態異常: アイコンを常設し、名前は長押し時だけ表示
- ターン切替: 中央の解決エリアを一度だけ横切るトランジション

### 4.4 やらないこと

- 常時点滅
- 全カードの同時浮遊
- 毎回の長い演出
- 操作可能かどうかを文章で説明し続ける
- 色だけで敵味方や状態を区別する
- ダメージ値・ログ・状態名を同時に大量表示する

演出は「重要な情報が変化した時だけ」に限定します。

## 5. 試し切りモードの再設計

現状の試し切りは、CPUが「技1を使えるなら1回使う」という簡易AIです。これはルール検証としてもゲーム体験としても弱いです。

### P0: ルール検証モード

- CPUは固定行動
- ダメージ式、状態異常、勝利条件を確認できる
- 乱数を固定できる
- 「次の処理」を1ステップずつ進められる
- 技の解決前に入力を止める
- すべてのイベントを開発者向けに確認できる

### P1: チュートリアルモード

- 初回だけ、1操作ずつ説明
- 「カードを中央へ」「このカードへ装着」などの短いガイド
- ガイドは常設テキストではなく、操作可能箇所のハイライトで示す
- 1ターン目は敵の行動を制限
- 1つの新要素を1ターンに1個だけ解禁

### P2: 実戦練習モード

- CPUの難易度を3段階にする
- 攻撃優先、守備優先、パーツ活用などの性格を持たせる
- プレイヤーの勝因・敗因を結果画面に出す
- 「このターンに使えた最善手」を任意で表示
- 実戦と同じカード配置・手札補充・パーツルールを使う

試し切りと対人バトルのルールを別物にしないことが最重要です。

## 6. カード生成との接続

カード生成では、生成成功とバトルで実際に使えることを分離する必要があります。

### 保存前に必須にする検証

- すべての技効果が実行エンジンで対応済みか
- targetが技種別に対して合法か
- passiveに実行条件があるか
- activeのコストが100か
- statusの意味が定義済みか
- パーツが親アクションに紐づいているか
- サポートがアクター用ステータスを持っていないか
- 1枚あたりの技数、効果数、数値上限が範囲内か

### 未対応効果の扱い

`effect_skipped`で試合を続行するのではなく、カードを `generation_status = failed` にして再生成するべきです。

プレイヤーにとって「このカードの技は発動したが何も起きなかった」は、最も信頼を失う不具合です。

## 7. 優先度付きロードマップ

### P0: ルール破綻を止める

- TypeScriptとSQLの仕様差分一覧を作成
- アクションカードの `deck / hand / field / discard` 遷移を実装
- 場の上限、補充、勝利条件を固定
- 技のtarget検証をサーバー側で強制
- skill conditionsを実行
- 未対応効果の保存を禁止
- 試し切りと対人で同じシナリオテストを実行
- 勝敗後、操作・同期・フリックを無効化

### P1: プレイ体験を成立させる

- フリックの解決プレビュー
- パーツと親カードの吸着演出
- カード詳細ボトムシート
- 状態異常アイコン化
- 現在カードのAPを主表示
- 手番ごとの入力可能・不可能の明確化
- CPUを固定AIから行動方針AIへ更新
- 結果画面に勝因・敗因を追加

### P2: 深さと気持ちよさを追加する

- 乱数計算の内訳表示
- リプレイ / ターン履歴
- CPU難易度
- カードごとの演出差分
- 連続技・反撃・追撃の専用演出
- リッチな動的CSS
- アクセシビリティ用のテキストログ切り替え
- リプレイ可能なイベントログの圧縮保存

## 8. 直近で作るべき受け入れテスト

### 配置

- 手札のアクションを場へ出せる
- 場が満杯なら出せない
- 場から破壊されたら、規定タイミングで手札から補充される
- パーツは親アクションにだけ装着できる
- パーツを2枚装着した後は3枚目を拒否する
- 装着済みパーツがリロード後も残る

### 行動

- 自分のターン以外は全ての入力が拒否される
- active技は必ず100 APを消費する
- AP不足時は実行されない
- passive技は条件成立時だけ発動する
- 技のtarget以外には効果が適用されない
- `stun`、`burn`、`guard_break`、`overdrive`の意味がそれぞれ異なる
- counterは被弾時に1回だけ発動する
- follow_upは命中時だけ発動する

### 同期

- 同じactionIdは二重適用されない
- 古いstate_versionの操作は拒否される
- 片方のプレイヤーの操作後、もう片方の盤面が同じ結果になる
- ネットワーク再接続後に手札・場・AP・パーツが一致する
- 勝敗確定後に遅延した操作が適用されない

---

## 最終方針

このゲームは、情報を常時見せるゲームではなく、**カードを動かすと必要な情報が現れ、結果が解決エリアに集約されるゲーム**にすると強くなります。

ただし、その体験を成立させる前提は、派手なCSSではありません。

> プレイヤーがカードを動かした結果と、ゲームルールが実際に適用した結果が、常に一致すること。

まずP0でルールを一本化し、その後P1でフリックと段階表示を完成させ、P2で演出を足す順序が適切です。
