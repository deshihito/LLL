# カードゲームUI再設計 改善案

## 1. 結論

現在のUIは「バトル画面の中に小さなカードが並ぶ」構成になっており、カードゲームとして重要な以下の要素が弱く見えています。

- 手札が独立したゲーム領域として見えない
- カードを引く、選ぶ、場に出すという流れが視覚的に伝わりにくい
- カードの表面・厚み・影・選択状態が弱く、紙やカードを扱う感覚がない
- 技・ログ・状態情報がカードの外側に分散している
- 「どのカードを操作しているのか」が一目で分からない

したがって、次の方針で再設計するのが適切です。

> **画面を操作するのではなく、カードを操作してバトルを進めるUIにする。**

3D表現は導入すべきですが、最初からThree.js/WebGLへ移行するのではなく、まずCSS 3Dを使ってカードの手触りを作るのが安全です。ゲームルール・状態管理は既存のバトルエンジンを正とし、UIだけをカード中心に再構成します。

---

## 2. 現状の課題

### 手札の課題

現在は手札が横並びの小さいカード一覧として表示されるため、次の問題があります。

- 「ここが手札である」という視覚的な区切りが弱い
- カードの種類、使用可能状態、選択中状態が小さく見える
- 手札から場へ移動する方向が明確ではない
- フリック操作とタップ操作の役割が分かりにくい
- 手札カードの表裏、重なり、手元に持っている感覚がない

### カード操作の課題

カードクリック後のモーダルは導入されていますが、カードゲームの主役であるカードがまだ「ボタンの入れ物」に見えます。

- 選択対象がカードではなく画面上のUIに見える
- 技の選択とカードの状態が結びついていない
- アクション、サポート、パーツの出し方が同じ導線に見える
- クリック、フリック、装着の関係が視覚的に説明されていない

### 質感の課題

現在のカードは画像と枠線が中心です。カードらしさを出すには以下が不足しています。

- カードの厚み
- 表面の反射
- 選択時の傾き
- カードを持ち上げたときの影
- 場に置いたときの接地感
- レアリティやタイプごとの素材差

---

## 3. 改善方針

### 基本レイアウト

PCとスマホで完全に別UIにするのではなく、以下の4ゾーンを共通概念として持たせます。

```text
┌──────────────────────────────┐
│ ターン / AP / 対戦情報 / 三線ログ │
├──────────────────────────────┤
│ 相手の場                       │
│                              │
│        中央のプレイゾーン       │
│                              │
│ 自分の場                       │
├──────────────────────────────┤
│ 手札：カードを持って操作する領域 │
└──────────────────────────────┘
```

手札は単なる一覧ではなく、画面下部に固定された「カードを持つ場所」として扱います。

---

## 4. 手札の再設計

### 4.1 手札専用のカードレール

現在の `.minimal-hand-row` を、単なる横スクロールリストではなく、手札専用レールへ変更します。

#### 表示仕様

- 手札領域に「HAND / 手札」の明確なラベルを表示
- カードを少し重ねて表示し、手元に持っている印象を出す
- 選択中カードだけ前面へ移動して拡大
- カード枚数を常に表示
- 手札領域の上端を明確な境界にする
- スマホでは画面下部に固定
- PCでは画面下部または盤面下端に固定

#### 状態表示

カードの状態は、カード上に直接表示します。

| 状態 | 表示 |
|---|---|
| 使用可能 | 明るいカード、浮いた影、操作可能カーソル |
| 選択中 | 上方向への移動、金色または青色の縁、拡大 |
| 使用済み | 彩度を落とす、斜線またはスタンプ、「使用済み」表示 |
| AP不足 | 暗くする、必要APを赤系で表示 |
| 破壊済み | 手札から消し、捨て札または破壊領域へ移動演出 |
| 対象選択待ち | カードを保持したまま、対象候補を発光 |

### 4.2 カードを「動かす」操作

操作はカードの種類によって明確に分けます。

#### アクションカード

- タップ：カードを選択して拡大
- カード内の技をタップ：技を発動
- 上方向フリック：プレイゾーンへ出す
- 場のカードをタップ：カード内の技を選ぶ

#### サポートカード

- タップ：カード詳細と効果を表示
- 上方向フリック：即時使用、または対象選択へ移行
- 使用後：手札から捨て札へ移動

#### パーツカード

- アクションカードへフリック
- 装着可能なカードだけ発光
- 不正な対象へ移動した場合は元の手札位置へ戻す

「中央へフリックしてください」というテキストだけで説明するのではなく、カードを動かした瞬間にプレイ可能な領域を発光させます。

### 4.3 フリック失敗時のフィードバック

操作失敗は単なるエラーテキストではなく、カードの動きで伝えます。

- 不正な方向：カードが元の位置へ戻る
- AP不足：カードが小さく揺れ、AP表示が強調される
- 対象不一致：対象候補だけが消灯し、正しい対象を発光
- ターン外：カードを少し持ち上げるが、プレイゾーンへ入らない

## 5. カードを一つのUIとして再設計

### 5.1 カードの構造

カードの中に、次の情報をまとめます。

```text
┌─────────────────┐
│ タイプ / コスト   │
│                 │
│    カード画像     │
│                 │
│ カード名          │
│ HP ATK DEF SPD   │
├─────────────────┤
│ 技1  名前  AP    │
│ 技2  名前  AP    │
│ 効果説明         │
└─────────────────┘
```

通常時はカードの表面を簡潔に表示し、カードを選択したときだけ下部の技領域を展開します。

### 5.2 モーダルからカード拡大ステージへ

現在のモーダルは一般的なダイアログに近いため、次のように改善します。

- カード本体を中央に大きく表示
- カードが手前に浮き上がるアニメーション
- カード本体の下または右側に技のスロットを配置
- 背景に盤面を残す
- カードを閉じるのではなく、再タップまたは下スワイプで戻す
- 「技を選ぶ」ではなく「このカードの技」という文脈を表示

これにより、常設の技一覧を削除しても、技がカード内に存在することが分かります。

## 6. CSS 3Dによるカードの質感

### 6.1 第一段階：CSS 3D

初期実装はCSS 3Dが適しています。

使用する要素：

- `perspective`
- `transform: rotateX / rotateY / translateZ`
- `backface-visibility`
- `box-shadow`
- `linear-gradient`
- `::before / ::after` による反射光
- Pointer位置に応じた傾き

カードにポインターを乗せた位置によって、カードが少しだけ傾きます。

```css
.card-3d {
  transform: perspective(900px) rotateX(var(--tilt-x)) rotateY(var(--tilt-y));
  transition: transform 180ms ease, box-shadow 180ms ease;
}

.card-3d.is-selected {
  transform: perspective(900px) translateY(-12px) scale(1.04)
    rotateX(var(--tilt-x)) rotateY(var(--tilt-y));
}
```

### 6.2 質感プリセット

カードタイプやレアリティに応じて素材を変えます。

| 種別 | 質感 |
|---|---|
| 通常 | マット紙、柔らかい影 |
| エリート | 少し光沢、紫系の縁 |
| レジェンド | 金属箔、金色の反射 |
| アクション | 深い青、硬質な枠 |
| サポート | 緑または白、薄い紙質 |
| パーツ | 工業素材、金属・機械的な縁 |

### 6.3 やりすぎを避ける

3Dは常時大きく回転させるのではなく、次の範囲に制限します。

- 通常時：傾き最大2〜3度
- 選択時：傾き最大5度
- フリック中：カードの移動を優先
- 使用時：一度だけ持ち上がり、プレイゾーンへ移動
- `prefers-reduced-motion`：変形・反射を無効化

WebGLやThree.jsを最初から導入すると、スマホの性能・バンドルサイズ・入力処理が複雑になるため、カードの表現だけならCSS 3Dで十分です。

## 7. カード状態をUIに反映する設計

既存のバトルエンジンには、すでに以下の状態があります。

- `hand`
- `actors`
- `discard`
- `defeated`
- `supportUses`
- `ap`
- `statuses`
- `equippedPartIds`

この状態をUI表示用に次のように正規化すると扱いやすくなります。

```ts
type CardPresentationState =
  | "hand-ready"
  | "hand-selected"
  | "hand-disabled"
  | "field-ready"
  | "field-selected"
  | "field-damaged"
  | "discarded"
  | "destroyed"
  | "targeting";
```

重要なのは、UI側で「使用済み」を独自に推測しないことです。

> **バトルエンジンの状態を唯一の正とし、UIはその状態をカードの見た目へ変換する。**

### 状態遷移の例

```text
手札
 ↓ タップ
選択中
 ↓ 上方向フリック
プレイゾーン
 ↓ 技を使用
場のカード / AP減少
 ↓ HPが0
破壊済み
 ↓ ルールに応じて
捨て札または場に残る
```

カードが画面から消えるだけではなく、どのゾーンへ移動したのかをアニメーションで伝える必要があります。

---

## 8. ログの扱い

三線メニューへの移行方針は維持します。ただし、ログを完全に隠すと状態が分からなくなるため、盤面上には短いフィードバックだけを残します。

- 技発動：カード上に「技発動」
- ダメージ：対象カード上に `-120`
- 回復：対象カード上に `+80`
- 破壊：カードに破壊スタンプ
- サポート消費：カードが捨て札へ移動

詳細な履歴だけを三線メニューへ移します。

これにより、ログを開かなくても盤面の変化は理解できます。

## 9. 実装優先順位

### Phase 1：手札をカードゲームとして見せる

最優先です。

- 手札専用レール
- カードの重なり
- アクション／サポート／パーツの種類表示
- 使用可能・使用済み・AP不足の状態表示
- 手札からプレイゾーンへのドラッグ／フリック演出
- タップとフリックの役割分離

### Phase 2：カードの3D質感

- CSS `perspective`
- 選択時の浮き上がり
- Pointer位置による微細な傾き
- 光沢レイヤー
- カードタイプごとの素材
- 場に出すときの接地アニメーション

### Phase 3：カード内の技選択

- カード本体を大きく表示
- カード下部に技スロットを表示
- 常設の技一覧を完全削除
- AP不足、条件未達成、ターン外をカード内に表示

### Phase 4：状態遷移アニメーション

- 手札から場へ移動
- 使用済みカードを捨て札へ移動
- 破壊カードを場から離脱
- AP変化のポップ表示
- 状態異常バッジの追加・消滅

### Phase 5：必要に応じたWebGL導入

CSS 3Dで表現できない場合のみ検討します。

導入条件：

- カード裏面・反転演出がゲーム体験上必須
- 複数カードの立体的な山札表現が必要
- 特殊カード演出に粒子や光源が必要
- CSS 3Dではスマホ性能を維持できない、または表現不足

通常のカード操作、手札、反射、傾きだけならWebGLは不要です。

## 10. 推奨する最終体験

ユーザーが次の流れを自然に理解できる状態を目標にします。

1. 画面下部に自分のカードが並んでいる
2. カードをタップすると手に取ったように浮き上がる
3. カードを上へフリックするとプレイゾーンへ移動する
4. 場に出たアクションカードをタップするとカードが拡大する
5. カード内に書かれた技を選ぶ
6. 技の結果がカードと盤面に直接反映される
7. 使用済みカードは捨て札へ移動する
8. 破壊されたカードは破壊状態として残る、またはルールに従い捨て札へ移る
9. 詳細な履歴は三線メニューで確認する

この流れが成立すれば、画面上の補助ボタンや説明文を大幅に減らしても、カードゲームとしての操作感と分かりやすさを両立できます。

---

## 11. 推奨判断

**実装すべきです。** ただし、いきなりThree.jsへ置き換えるのではなく、次の順番が最も効果的です。

1. 手札を独立したカードゾーンとして再設計
2. カードを主役にした操作導線へ統一
3. CSS 3Dで厚み・影・反射・浮き上がりを追加
4. 状態遷移アニメーションを追加
5. CSS 3Dで不足する演出だけWebGLを検討

現状のバトルエンジンは手札・場・捨て札・破壊・AP・技をすでに管理できるため、まずはゲームロジックを変更せず、カードUIと表示状態を再設計するのが安全です。
